Handling Peak Verification Traffic Smoothly — SyncETA Capacity Scaling (Part 1)

  • ApproachInstead of scaling on CPU usage, SyncETA monitors pending jobs in Redis Queue with KEDA to scale workers on demand while draining active runs safely.
  • ImpactTeams keep release-day verification times steady without paying for idle peak capacity during quiet hours.

SyncETA supports scheduled execution of automated screen checks. Under normal daily traffic, a fixed number of worker pods handles everything smoothly. During quarterly audits or major release windows, however, dozens of scenarios trigger at once—and if worker capacity stays fixed, pending jobs pile up quickly.

Manually scaling Kubernetes pods up before a release window and scaling them back down afterward defeats the purpose of an automated QA platform. We needed demand-driven worker scaling tailored to browser automation workloads.

1. Why Standard CPU/Memory HPA Was Not Enough

Kubernetes provides HPA (Horizontal Pod Autoscaler) out of the box based on CPU or memory utilization. However, each SyncETA worker pod runs one isolated scenario at a time, bundling a headless browser, worker process, and Playwright MCP server inside the container.

Even a single running scenario legitimately consumes a high share of the pod's allocated CPU and memory. Scaling purely on resource utilization would trigger unnecessary scale-outs even when only one job is running and no queue backlog exists. The true demand signal is how many scenarios are waiting in the queue.

2. Scheduled Execution Flow & Redis Queue Depth

SyncETA dispatches scheduled checks through a straightforward queue pipeline:

[WAS / Scheduler]
  User registers Cron schedule
            │
            ▼
  Enqueues Job into Redis Queue at trigger time
            │
            ▼
[Redis Queue]
  Pending Jobs waiting for execution (Queue Length = Backlog)
            │
            ▼
[SyncETA Worker Pod]
  Pulls Job and runs browser + Playwright MCP scenario

Because waiting jobs already accumulate in Redis Queue, scaling workers according to queue length matches real demand directly—bounded by a configured maximum pod ceiling to protect cluster resources.

3. Adopting KEDA (Kubernetes Event-Driven Autoscaling)

To scale Kubernetes workloads from queue metrics, we evaluated KEDA (Kubernetes Event-Driven Autoscaling). KEDA extends Kubernetes to autoscale deployments based on external event sources such as Redis, Kafka, and RabbitMQ.

Because KEDA's Redis scaler behavior depends on the exact underlying data structure (List, Stream, or queue library keys), our first implementation step is mapping the exact Redis key layout and consumption semantics used by SyncETA.

4. The Harder Problem: Safe Scale-In Without Aborting Active Tests

Scaling out when queue length rises is straightforward. Scaling back in safely is far trickier: even when Redis Queue length hits zero, running worker pods may still be mid-scenario. Terminating a busy pod immediately kills its browser and Playwright MCP session, causing false test failures.

Safe scale-in therefore requires pairing KEDA cooldownPeriod settings with graceful pod draining, preStop hooks, and adequate terminationGracePeriodSeconds so active runs complete cleanly before termination.
