# 📘 スクラムバン(Scrumban) 標準運用ガイド

## 1. 概要

スクラムバン(Scrumban)は、**スクラム(Scrum)** の構造と **カンバン(Kanban)** の柔軟なフロー管理方式を組み合わせたハイブリッドプロセスです。

- **スクラム**が提供するルール・役割・バックログ管理
- **カンバン**が提供するWIP制限、プル(Pull)システム、フローの視覚化
  この2つを組み合わせて、**変化に素早く適応**し、**フローを最適化**することが核心的な目的です。

> 🔑 **核心哲学**
> 「**Stop starting, start finishing**」 — 新しい作業を始めるよりも、進行中の仕事を終わらせよ。

---

## 2. 基本原則

1. **プル(Pull)ベースの作業**

- 作業はチームが処理可能な時にのみ開始します。
- 強制的に「押し込む」作業はフローを壊します。

2. **WIP(Work In Progress)制限**

- 同時に進行中の作業数を制限することで、品質低下やマルチタスクの問題を防ぎます。
- 例: チームメンバーが5人の場合、Doing WIP = 3。

3. **ワークフローの視覚化**

- カンバンボードですべての作業状態を一目でわかるように表示します。
- ボトルネックを即座に確認できます。

4. **明確なポリシー(Explicit Policies)**

- 各カラムへ移動できる条件(Definition of Ready / Doneなど)を文書化し、全チームメンバーで共有します。

5. **データに基づいた改善**

- サイクルタイム・スループット・WIP・CFD(累積フロー図)などを測定し、改善の方向性を決定します。

---

## 3. 役割と責任

| 役割 | 主な責任 | 備考 |
| ------------------------------- | --------------------------------------------------------------- | --------------------------------------------- |
| **Product Owner (PO)** | バックログ管理、優先順位設定、要件の明確化、ビジネス目標の伝達 | スクラムと同じまま維持 |
| **Flow Manager / Scrum Master** | WIPモニタリング、ボトルネック解消支援、振り返りの進行、プロセス改善の促進 | カンバンにおけるService Delivery Managerの概念と類似 |
| **チームメンバー(Dev/QAなど)** | WIP遵守、プルベースの作業、カード状態の更新、品質の保証 | 自律性と責任が必須 |
| **ステークホルダー** | フィードバックの提供、デモ/レビューへの参加 | 定期的な関与が必要 |

---

## 4. プロセス段階別アクティビティ

| 段階 | アクティビティ | 詳細説明 | ポリシー(例) |
| ----------- | ------------------------ | ---------------------------------------------------------- | ---------------------------------------------- |
| **Backlog** | リクエスト/アイデア収集 | 顧客の要望、バグ、技術的負債、新機能など、すべての作業の出発点 | すべてのカードに優先順位とClass of Serviceを指定 |
| **Ready** | DoR確認、作業準備完了 | 要件の明確化、リソース確保、テスト条件定義 | DoRチェックリスト通過時のみ移動 |
| **Doing** | 作業進行 | WIP制限内でプル(Pull)した後に開発/実装 | Doing WIP = 3 |
| **Review** | コード/ドキュメントレビュー | 品質、標準、セキュリティ、テストカバレッジの確認 | レビュアーの承認後、Testingへ移動 |
| **Testing** | 品質検証 | 自動・手動テスト、欠陥の修正 | QA完了時、Doneへ移動 |
| **Done** | 作業完了 | DoDを満たし、文書化/デプロイ完了、サイクルタイム記録 | 完了タグの付与 |

---

## 5. 定義(Definition)基準

### 5.1 Definition of Ready (DoR)

- 要件が明確で文書化されている
- 必要なデザイン/リソースが確保されている
- テスト条件が定義されている
- 予想される作業範囲・難易度が確認されている

### 5.2 Definition of Done (DoD)

- コードのマージおよびビルド成功
- 自動・手動テスト通過
- ドキュメント/リリースノート作成
- デプロイ(または顧客への引き渡し)完了

---

## 6. 会議(Event)運用ガイド

| 会議 | 目的 | 周期 | 時間 | 特徴 |
| --------------------------- | -------------------- | ------------------- | -------- | ----------------------- |
| **Daily Stand-up** | 進捗状況、ボトルネックの共有 | 毎日 | 10~15分 | カラムのフローを中心とした議論 |
| **Replenishment** | Ready カラムの補充 | 週1回 or 限界値到達時 | 30分 | 優先順位の再調整 |
| **Retrospective** | プロセスの改善 | 2~4週ごと | 30~60分 | WIP・ポリシーの調整 |
| **Service Delivery Review** | SLA/SLEレビュー | 月1回 | 30分 | 指標に基づいたレビュー |

---

## 7. WIP制限の運用

- 初期値: `チームメンバー数 ÷ 2`
- カラム別WIPの例:

  - Doing: 3
  - Review: 2
  - Testing: 2

- WIP超過時は直ちに原因分析(ボトルネック、人員不足、ブロッカーなど)
- 解決するまで新規作業の開始を禁止

---

## 8. メトリクス管理

| 指標 | 定義 | 活用 |
| --------------- | ---------------------- | -------------------- |
| **リードタイム** | リクエスト発生 → 完了 | 顧客の待機時間の分析 |
| **サイクルタイム** | 作業開始 → 完了 | フローの安定性の測定 |
| **スループット** | 一定期間に完了したカード数 | 生産性の予測 |
| **平均WIP** | 進行中の作業の平均 | ボトルネック・マルチタスクの防止 |
| **CFD** | カラム別の累積作業数 | ボトルネック区間の把握 |

> **Tip:** リトルの法則 (Little’s Law) を活用する
> `WIP = Throughput × Cycle Time`
> → WIP・スループット・サイクルタイムのいずれかを調整すると、残りの要素が変化します。

---

## 9. 運用ルールの例

1. プル(Pull)前に必ずWIPを確認
2. すべてのカードに優先順位・担当者を指定
3. ブロッカーを直ちに表示(ステッカー/ラベル)
4. 会議時間は厳格に制限(Stand-up ≤ 15分)
5. プロセスの変更は振り返りで合意した後に反映

---

## 10. プロセスの視覚化例

```
[Backlog]
  ↓ (Replenishment)
[Ready]
  ↓ (Pull & WIP Check)
[Doing]
  ↓ (開発完了)
[Review]
  ↓ (レビュー承認)
[Testing]
  ↓ (品質検証完了)
[Done]
```

---

## 11. 改善サイクル

1. メトリクスの収集 (サイクルタイム、スループット、WIP)
2. ボトルネックおよび変動性の分析
3. WIP制限・ポリシー・ボード構造の調整
4. 1〜2週間のテスト適用
5. 振り返りで効果を検証後、確定

---

## 12. 付録

### Classes of Service の例

- **Expedite**: 直ちに処理(緊急)
- **Fixed Date**: 特定の日に締め切り
- **Standard**: 一般的なリクエスト
- **Intangible**: 技術的負債などの長期的な価値

### 推奨ツール

- Jira, Trello, Azure DevOps, Miro, ClickUp

---

**📌 核心メッセージ**
スクラムバンは「**ルールを最小限に維持し、フローを最適化する**」方法論です。
プロセスは、チームの**データと合意**に基づいて継続的に進化させる必要があります。
