SyncETA 自動拡張運用記 (2) — KEDA ScaledObjectと実行中テストを守る安全な縮小設計

経営層・現場担当者のための3行要約
  • 従来の課題待機キューが0になった瞬間にワーカーを縮小すると、実行中ブラウザテストを抱えるPodが強制終了されテスト失敗を招きます。
  • 解決アプローチBullMQの待機・実行両キー（bull:scheduler_jobs:wait / active）をKEDAで監視し、180秒終了猶予・ゾンビ回収・安定化ウィンドウを組み合わせています。

1. SyncETAワーカー構造とBullMQ Redisキー

SyncETAはAPIとワーカーで同一イメージを共有し、APP_ROLE=worker指定時のみworker-main.tsがHTTPサーバーを立てずにSchedulerJobProcessorを起動してBullMQ scheduler_jobsキューを処理します。

  • 待機キュー（bull:scheduler_jobs:wait）：まだワーカーに取得されていない実行待ちシナリオ。
  • 実行中キュー（bull:scheduler_jobs:active）：ワーカーが取得しヘッドレスブラウザで実行中のシナリオ。

waitだけを監視すると全ジョブがactiveに移った直後に縮小判定が走るため、waitとactiveの両方を監視対象とするのが要点です。

2. KEDA ScaledObject と認証設計

Redis認証情報はKubernetes SecretとTriggerAuthenticationで分離管理します。

apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata:
  name: sync-eta-redis-auth
  namespace: sync-eta
spec:
  secretTargetRef:
    - parameter: password
      name: worker-secret
      key: REDIS_PASSWORD
---
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: sync-eta-worker-scaler
  namespace: sync-eta
spec:
  scaleTargetRef:
    name: worker
  pollingInterval: 15
  cooldownPeriod: 300
  minReplicaCount: 2
  maxReplicaCount: 12
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp:
          stabilizationWindowSeconds: 0
          policies:
            - type: Pods
              value: 4
              periodSeconds: 30
        scaleDown:
          stabilizationWindowSeconds: 300
          policies:
            - type: Pods
              value: 1
              periodSeconds: 60
  triggers:
    - type: redis
      metadata:
        address: redis.sync-eta.svc.cluster.local:6379
        listName: bull:scheduler_jobs:wait
        listLength: "1"
      authenticationRef:
        name: sync-eta-redis-auth
    - type: redis
      metadata:
        address: redis.sync-eta.svc.cluster.local:6379
        listName: bull:scheduler_jobs:active
        listLength: "1"
      authenticationRef:
        name: sync-eta-redis-auth

3. 実行中テストを守る4重の終了保護

  1. terminationGracePeriodSeconds: 180：SIGTERM後に進行中シナリオと.webm動画保存を完了する猶予を確保します。
  2. shareProcessNamespace: true：ヘッドレスChromiumの子プロセスがゾンビ化しないようPID 1で確実に回収します。
  3. BullMQのSIGTERMグレースフル終了：app.close()により新規ジョブ取得を止め、処理中ジョブ完了後に安全停止します。
  4. ノード保護とコントロールプレーン分離：nodeAffinityでマスターノード配置を除外し、リソース上限（CPU 2.3 / メモリ 4Gi）でkubelet余力を確保します。

4. 本番検証チェックリスト

  • 20件の同時スケジュール実行時にkubectl get hpa -n sync-eta -wで期待通りに拡張することを確認します。
  • 縮小時間帯に実行中テストの中断や動画証跡の欠損が発生しないことを検証します。
  • Prometheus/GrafanaでOOM発生や残留Chromiumプロセスがゼロであることを継続監視します。
