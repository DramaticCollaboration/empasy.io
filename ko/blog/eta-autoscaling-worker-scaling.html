  • 기존 문제정기 업데이트 직전에 수십 건의 화면 점검 요청이 한꺼번에 몰리면 대기 시간이 길어져 배포 일정이 지연됩니다.

SyncETA는 테스트 시나리오를 정해진 시각에 자동 실행할 수 있는 스케줄 기능을 제공합니다. 평상시에는 고정 워커 수로도 무리 없이 동작하지만, 분기별 정기 점검이나 대규모 배포 직전처럼 특정 시간대에 시나리오가 한꺼번에 몰릴 때는 워커가 부족해 실행 대기열이 빠르게 길어집니다.

그렇다고 점검 일정이 몰릴 때마다 담당자가 수동으로 Kubernetes Pod 수를 늘리고 작업이 끝나면 다시 줄이는 방식은 지속 가능하지 않습니다. 테스트 자동화 솔루션을 운영하면서 정작 실행 인프라 증설을 수동에 맡길 수는 없기 때문입니다.

1. 기본 HPA(CPU · 메모리 기준)가 맞지 않았던 이유

Kubernetes에는 CPU나 메모리 사용률을 기준으로 Pod 수를 자동 조절하는 HPA(Horizontal Pod Autoscaler)가 기본 제공됩니다. 처음에는 SyncETA 워커에도 HPA를 바로 적용하는 방안을 검토했지만, 워커의 실행 구조를 살펴보니 중요한 제약이 있었습니다.

SyncETA 워커 Pod 하나는 한 번에 하나의 시나리오를 격리 실행합니다. 각 Pod 내부에서 헤드리스 브라우저, 워커 프로세스, Playwright MCP 서버가 함께 구동되기 때문에 시나리오 단 1건만 실행 중이어도 할당된 CPU와 메모리를 높게 사용합니다.

따라서 단순 리소스 사용률을 기준으로 오토스케일링을 걸면, 대기열이 비어 있고 시나리오가 고작 하나 실행 중일 때도 불필요하게 Pod가 증설되는 오동작이 발생할 수 있습니다. 핵심 지표는 리소스 사용률이 아니라 실행을 기다리고 있는 대기 시나리오 수였습니다.

2. 스케줄 실행 흐름과 Redis Queue 대기열 기준

현재 SyncETA의 스케줄 실행 파이프라인은 다음과 같은 구조로 동작합니다.

[WAS / Scheduler]
  사용자가 Cron 스케줄 등록
            │
            ▼
  실행 시점에 Redis Queue에 Job 등록
            │
            ▼
[Redis Queue]
  실행 대기 중인 Job 적재 (Queue Length = 대기 건수)
            │
            ▼
[SyncETA Worker Pod]
  Job을 가져와 브라우저 + Playwright MCP로 시나리오 실행

이미 실행 대기 작업이 Redis Queue에 쌓이고 있으므로, 대기열 길이를 스케일링 기준 지표로 삼으면 실제 수요에 정확히 비례해 워커를 늘릴 수 있습니다. 예를 들어 기존 워커가 모두 작업 중이고 대기 Job이 10건 쌓였다면, 사전에 설정한 최대 Pod 한도 내에서 필요한 만큼 워커를 즉시 추가 기동하는 방식입니다.

3. KEDA(Kubernetes Event-driven Autoscaling) 검토

외부 큐 지표를 기준으로 워크로드를 확장하기 위해 KEDA(Kubernetes Event-driven Autoscaling)를 도입 대상으로 선정했습니다. KEDA는 CPU·메모리 지표뿐 아니라 Redis, Kafka, RabbitMQ 등 외부 이벤트·대기열 길이를 직접 감지해 Kubernetes Deployment를 자동 확장·축소할 수 있는 오픈소스 도구입니다.

다만 Redis를 사용한다고 설정 한 줄로 끝나는 것은 아닙니다. SyncETA 내부에서 Queue가 List, Stream, 혹은 BullMQ 구조 중 어떤 형태로 구현되어 있는지에 따라 KEDA의 Scaler 종류와 대기 건수 측정 방식이 달라지므로, 먼저 실제 키 구조와 소비 패턴을 정밀하게 확인해야 합니다.

4. 늘리는 것보다 중요한 과제: 안전한 축소(Graceful Scale-In)

대기 Job이 늘었을 때 워커를 증설하는 흐름은 비교적 명확합니다. 진짜 까다로운 지점은 작업이 마무리되어 대기열이 0이 되었을 때 워커를 어떻게 안전하게 줄이느냐입니다.

Redis Queue가 비어 있더라도, 이미 Job을 꺼내 간 워커 내부에서는 브라우저 테스트 시나리오가 한창 실행 중일 수 있습니다. 이 시점에 Pod가 강제 종료되면 브라우저와 MCP 서버가 함께 내려가 정상 진행 중이던 테스트가 실패로 끊기게 됩니다.

따라서 Queue 길이 기반 확장뿐 아니라 terminationGracePeriodSeconds, preStop 훅, 실행 중 작업 완료 대기(Draining) 및 KEDA cooldownPeriod 정책을 함께 설계해야 합니다.

5. 다음 편 보기: KEDA 설치 및 Redis Queue 실전 연동

목표는 분명합니다. 대기 시나리오가 쌓이면 워커 Pod가 자동으로 확장되고, 작업이 줄어들면 실행 중인 시나리오를 안전하게 마친 뒤 Pod가 축소되는 구조를 완성하는 것입니다. 실제 SyncETA BullMQ 큐(scheduler_jobs) 연동과 KEDA ScaledObject·안전한 종료 정책 구현은 2편: KEDA ScaledObject와 실행 중 테스트를 보호하는 안전한 축소 구현에서 바로 확인하실 수 있습니다.

엔지니어링 노트 (작성자 메모)
