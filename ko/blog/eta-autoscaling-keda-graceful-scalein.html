SyncETA 자동 확장 적용기 (2) — KEDA ScaledObject와 실행 중 테스트를 보호하는 안전한 축소 구현

경영진 · 현업 담당자를 위한 3줄 요약
  • 기존 문제1편에서 확인했듯 Redis Queue 대기열만 보고 워커를 즉시 줄이면, 이미 시나리오를 실행 중인 브라우저 Pod가 강제 종료되어 정상 테스트가 실패로 끊깁니다.
  • 해결 방식BullMQ 대기·실행 키(bull:scheduler_jobs:wait / active)를 KEDA ScaledObject에 연결하고, 180초 종료 유예(terminationGracePeriodSeconds)·좀비 프로세스 회수(shareProcessNamespace)·안정화 윈도우를 결합합니다.
  • 기대 효과점검 요청이 몰릴 때는 최대 한도까지 빠르게 확장하고, 작업이 끝나면 실행 중 시나리오를 안전하게 마친 워커만 순차적으로 축소합니다.

1편(워커를 언제 늘려야 할까?)에서는 SyncETA 워커 Pod에 CPU·메모리 기준 HPA가 맞지 않는 이유와 Redis Queue 대기열 길이 기반 확장의 필요성을 정리했습니다. 이번 2편에서는 실제 SyncETA의 BullMQ 큐 구조(scheduler_jobs)와 Kubernetes 워커 Deployment(APP_ROLE=worker)를 바탕으로, KEDA ScaledObject 구성과 실행 중 테스트를 보호하는 안전한 축소(Graceful Scale-In) 구현 세부 사항을 공유합니다.

1. SyncETA 워커 실행 구조와 BullMQ Redis 키 확인

SyncETA 백엔드는 API 서버와 워커가 동일한 컨테이너 이미지를 사용하되, 환경 변수 APP_ROLE=worker로 역할을 분리합니다. 워커 프로세스(worker-main.ts)는 HTTP 서버를 띄우지 않고 NestFactory.createApplicationContext로 컨텍스트만 기동해 SchedulerJobProcessor가 BullMQ scheduler_jobs 큐를 소비하도록 설계되어 있습니다.

  • 대기 중인 잡 키(bull:scheduler_jobs:wait): 스케줄러가 등록해 아직 워커가 가져가지 않은 대기 시나리오 목록(Redis List)입니다.
  • 실행 중인 잡 키(bull:scheduler_jobs:active): 워커가 이미 가져가 헤드리스 브라우저와 Playwright MCP로 실행 중인 시나리오 목록입니다.

여기서 중요한 포인트가 드러납니다. 만약 wait 키만 트리거로 감시하면, 대기 잡이 모두 워커에 할당되어 wait=0이 되는 순간 KEDA가 작업을 끝난 것으로 오판해 축소를 시도할 수 있습니다. 따라서 wait와 active 두 지표를 함께 감시해야 실행 중 부하가 정확히 반영됩니다.

2. KEDA ScaledObject 및 인증 설정 설계

Redis 접속 비밀번호는 매니페스트에 평문으로 넣지 않고 Kubernetes Secret과 KEDA TriggerAuthentication으로 분리 참조합니다. 아래는 SyncETA 워커 Deployment(namespace: sync-eta)를 대상으로 wait와 active 큐를 함께 감시하는 ScaledObject 구성 예시입니다.

apiVersion: keda.sh/v1alpha1
kind: TriggerAuthentication
metadata:
  name: sync-eta-redis-auth
  namespace: sync-eta
spec:
  secretTargetRef:
    - parameter: password
      name: worker-secret
      key: REDIS_PASSWORD
---
apiVersion: keda.sh/v1alpha1
kind: ScaledObject
metadata:
  name: sync-eta-worker-scaler
  namespace: sync-eta
spec:
  scaleTargetRef:
    name: worker
  pollingInterval: 15
  cooldownPeriod: 300
  minReplicaCount: 2
  maxReplicaCount: 12
  advanced:
    horizontalPodAutoscalerConfig:
      behavior:
        scaleUp:
          stabilizationWindowSeconds: 0
          policies:
            - type: Pods
              value: 4
              periodSeconds: 30
        scaleDown:
          stabilizationWindowSeconds: 300
          policies:
            - type: Pods
              value: 1
              periodSeconds: 60
  triggers:
    - type: redis
      metadata:
        address: redis.sync-eta.svc.cluster.local:6379
        listName: bull:scheduler_jobs:wait
        listLength: "1"
      authenticationRef:
        name: sync-eta-redis-auth
    - type: redis
      metadata:
        address: redis.sync-eta.svc.cluster.local:6379
        listName: bull:scheduler_jobs:active
        listLength: "1"
      authenticationRef:
        name: sync-eta-redis-auth
  • 빠른 확장, 완만한 축소: scaleUp.stabilizationWindowSeconds: 0으로 몰리는 점검 요청에 30초당 최대 4개 Pod까지 즉시 대응하고, scaleDown은 300초 안정화 창과 분당 1개 Pod 제한으로 잦은 출렁임(Flapping)을 방지합니다.
  • 클러스터 자원 한계 보호: maxReplicaCount를 워커 노드 풀의 가용 CPU·메모리(브라우저 1개당 안정 기준 CPU 1 Core / RAM 2Gi)에 맞춰 명시적으로 제한합니다.

3. 실행 중 테스트를 보호하는 4중 안전 종료 장치

KEDA 설정만으로는 충분하지 않습니다. Kubernetes Deployment와 Node.js/BullMQ 워커 레벨이 함께 맞물려야 실행 중 시나리오 중단과 브라우저 좀비 프로세스를 예방할 수 있습니다.

  1. terminationGracePeriodSeconds: 180 확보: SyncETA 워커 매니페스트(worker.yaml)에 180초 종료 유예 시간을 부여해, SIGTERM 수신 후 진행 중인 시나리오와 영상(.webm) 업로드가 완료될 시간을 보장합니다.
  2. shareProcessNamespace: true 적용: 헤드리스 Chromium 서브프로세스가 비정상 종료 후 좀비로 남지 않도록 Pod 내부 프로세스 네임스페이스 공유로 PID 1이 잔여 프로세스를 깔끔히 회수합니다.
  3. BullMQ 워커 SIGTERM 드레이닝: 워커 애플리케이션이 SIGTERM을 받으면 app.close()를 호출해 새 잡 폴링을 즉시 멈추고 현재 처리 중인 잡이 끝난 뒤 정상 종료합니다.
  4. 노드 안정성 및 마스터 격리: nodeAffinity로 컨트롤 플레인 노드 배치를 제외하고, 컨테이너 리소스 limits(CPU 2.3 / Memory 4Gi)에 kubelet 시스템 여유분을 남겨 워커 급증 시 노드 NotReady 현상을 예방합니다.

4. 운영 검증 체크리스트

  • 버스트 테스트: 동일 시각에 20건의 Cron 시나리오를 동시 투입했을 때 kubectl get hpa -n sync-eta -w에서 목표 Pod 수가 wait + active 합산치에 맞춰 확장되는지 확인합니다.
  • 종료 무결성 검증: 축소가 시작되는 구간에서 실행 중인 테스트의 결과 로그와 .webm 증적 파일이 누락·중단 없이 정상 완료(Pass/Fail 판정)로 기록되는지 대조합니다.
  • 자원 여유 모니터링: Prometheus/Grafana에서 워커 노드의 메모리 압박(OOMKilled)과 잔여 Chromium 프로세스 수가 0으로 유지되는지 추적합니다.
